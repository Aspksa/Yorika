# YORIKA — генеральная дорожная карта всего проекта

**Срез:** 19 октября 2026. **Опорный код:** `main` после PR #164 (`b7d92cb2719c771f50b13694e172d8e6084dc871`).  
**Последняя функциональная интеграция:** PR #163, многосессионный тренировочный сценарий.  
**Цель:** локальная Windows-помощница Yorika с интерфейсом и аватаром кицунэ, собственным обученным языковым Transformer, устойчивой памятью, голосом, разумной инициативой, управляемыми инструментами и проверяемой эволюцией модели.  
**Документы:** [видение](YORIKA_VISION.md) · [краткий план и история PR](ROADMAP.md) · [реестр 100 задач](../planning/tasks.json) · [архитектура](ARCHITECTURE.md) · [аудит](STATUS_AUDIT.md).

> **Как читать статусы.** **Реализовано в коде** означает наличие компонента, а не гарантию полноценной работы на компьютере пользователя. **Частично** — есть прототип/часть пути, но не завершена приёмка. **Не выполнено** — отсутствует нужный результат или нет надёжного свидетельства. Источником машинных статусов остаётся `planning/tasks.json`; этот документ — целостная карта зависимостей и фактических ограничений. Не подменять «инженерный код готов» утверждением «Yorika обучена и функционирует как полноценный собеседник».

## 0. Где мы остановились

**Точка остановки: завершён PR #164, а последняя функциональная работа — PR #163.** Существует экспериментальный собственный UTF-8/BPE Transformer; реализованы инфраструктура train/validation/test, контроль метаданных корпуса, checkpoint с сохранением оптимизатора/RNG, выбор best checkpoint, независимое измерение NLL/perplexity, код CUDA-тренировки и многосессионный запуск. Короткие CPU PyTorch GitHub Actions проходили. **Это ещё не готовый русский «мозг» в продукте.**

**Три блокирующих фактических результата:**
1. **Реальный большой русский корпус с подтверждёнными правами и качеством — не получен.** Записанные вручную флаги consent/license/rights review не заменяют юридическую проверку и происхождение данных.
2. **Продолжительное RTX 3050 CUDA-обучение — не выполнялось.** Нет протоколов фактического многодневного прогона, аппаратной приёмки VRAM и восстановления на пользовательском GPU.
3. **Измеримое улучшение русского диалога — не доказано.** Held-out NLL и учебные тесты не заменяют независимое сравнение ответов и слепую оценку людьми.

**Следующее практическое действие:** получить допустимый реальный корпус → независимо проверить права и качество → провести короткую реальную приёмку CUDA/VRAM/checkpoint на RTX 3050 → длинный контролируемый прогон → blind benchmark → только после этого подключать принятый checkpoint к продукту. Без данных и GPU не расширять тренировочные обёртки ради видимости прогресса.

## 2. Подробная дорожная карта по направлениям

### A. Фундамент Windows, установка и надёжность — P0

**Сделано в коде:** `Yorika.bat` → PowerShell/трей → localhost; случайный свободный порт, mutex, UTF-8, статус/лог; без отдельного окна лаунчера; минимальный сайт не требует Python. Есть тестовые скрипты и GitHub PowerShell validation.

**Частично:** обновления/rollback, диагностика ошибок, восстановление после аварий. Историческая документация о функциях обновления неоднородна: наличие скриптов/тестовых кнопок не равнозначно безопасной установке на рабочую папку.

**Дальше:** проверка PowerShell 5.1 и Windows 10/11; пути с кириллицей; запуск без Python; две вкладки и повторный запуск; убийство процесса; отказ диска; безопасный отказ при битых настройках; тестовая установка и rollback только на отдельной копии; установочный manifest и интеграционные Windows-свидетельства.

**Критерий:** полный живой Windows E2E-протокол с воспроизводимыми командами/артефактами, без потери данных; `BASE-004`, `QA-003`.

### B. UI, аватар, характер и доступность — P1

**Сделано:** страницы сайта, `www/avatar.js`, панели настроек/обновлений, основная оболочка чата и графический образ.

**Частично:** динамические реплики/сценарии, состояния аватара, удобство основных режимов.

**Дальше:** закрепить контракт «получен токен → показан в чате → озвучен → отражён аватаром»; анимации не должны притворяться интеллектом; визуальные настройки, история диалога, клавиатура, screen reader, reduced motion, адаптивный дизайн; развить реальные многошаговые ветвящиеся сценарии с тестами переходов.

**Критерий:** приёмка на основных браузерах и Windows, отсутствие ложных статусов «думает/обучается/сделала» без событий.

### C. Данные, резервное копирование и долговечная память — P0/P1

**Сделано в коде:** `backend/storage.py`, `scripts/chat-store.py`, SQLite-транзакции/ревизии; браузерные IndexedDB/localStorage; ручной экспорт и импорт; обработка конфликтов в отдельных сценариях.

**Не закрыто:** проблема зависимости браузерного хранилища от случайного localhost-порта, автоматическая миграция из старых origin, проверенное восстановление, шифрование и миграции версий схем.

**Следующие шаги:** единый основной storage вне каталога установки; стабильные ID сообщений; протокол merge нескольких вкладок; backup/restore с проверкой контрольных сумм; миграции версии БД; сценарии пропажи питания; поиск с происхождением, возможность исправить/удалить память; гарантированная связь истории с пользователем и её согласованная политика хранения.

**Критерий:** сохранение истории при рестарте, смене порта/релиза, отказах и конкурентных записях; подтверждённые тесты `DATA-001`–`003` и `MEMORY-001`–`003`.

### D. Локальный backend и API — P0

**Сделано частично:** экспериментальные Python endpoints и пути подключения истории и собственного нейроответчика. Базовый сайт независим от Python.

**Дальше:** optional backend bootstrap в Windows стартере; локальная авторизация API, CSRF/DNS-rebinding/origin защита, лимиты размеров и времени, понятные ошибки; health/status; процессы и логи без секретов; очередь запросов и отмена; отдельные границы UI, API, inference и storage.

**Критерий:** безопасный E2E запрос чата/сохранения/отмены с реального браузера и отказ при неавторизованном доступе; `API-001`/`002`.

### E. Собственная языковая модель — P0 для «первого мозга»

**Реализовано в коде (PR #149–#163):**
- Русскоязычный byte-level UTF-8/BPE с контролем версии tokenizer.
- Экспериментальный autoregressive Transformer одной архитектуры; проверенная конфигурация порядка 5–10 млн параметров.
- Token-level learning с mask для диалогов, train/validation/test и SHA manifests.
- AdamW, clipping, сохранение RNG/optimizer/cursor, защита от несовместимых checkpoint, отдельный best по validation NLL.
- CPU/CUDA выбор устройства, GPU tensors, контроль выделения VRAM, ограничения времени и многосессионный сценарий.
- Независимый token-weighted NLL/perplexity, однократный финальный test, benchmark двух checkpoint и запрет silent fallback на внешнюю LLM.
- CI на коротком CPU-тестовом корпусе и условные CUDA-тесты, которые требуют отдельного GPU runner.

**Не сделано:** продуктово обученная качественная русская модель. Нельзя считать «5–10 млн параметров» достаточным качеством общения. Настоящая RTX 3050, смешанная точность и долговременная устойчивость требуют приёмки.

**Дальше:** корпус → GPU-прогон → сравнение с baseline → отбор → controlled rollout → регрессионные сценарии чата. При отсутствии улучшения оставлять старую модель, а не автоматически активировать экспериментальную.

**Критерий:** подписанная/проверенная цепочка dataset→config→checkpoint→held-out evidence→decision; `BRAIN-001`–`007` остаются по реестру незакрытыми до соответствующей конечной приёмки, несмотря на реализованные подкомпоненты.

### F. Большой русский корпус и лицензии — P0, первый блокер

**Есть:** schema и fail-closed фильтры разрешения, происхождения, секретов, дедупликации prompt, разбиения и metadata review.

**Нет:** реально переданных и проверенных >=10 000 содержательных русских диалоговых записей нужного качества и соответствующих прав. «Public-domain» или «synthetic» как надпись в JSON не является независимым доказательством.

**План:** правовой каталог источников (правообладатель, лицензия, URL/документ, дата проверки, применимые ограничения, разрешение на обучение); безопасный импорт без персональных сведений; Unicode нормализация; near-duplicate очистка; контроль токсичности/утечек; ручная выборочная оценка; train/validation/test на уровне источника и смысловых дублей; неизменяемый dataset card и версионирование.

**Критерий:** содержательный корпус с реальными подтверждёнными правами, аудитом и фиксированным тестовым разделом. Не создавать искусственные тысячи однотипных реплик ради галочки.

### G. GPU-обучение RTX 3050 — P0, второй блокер

**Есть:** `scripts/probe-language-cuda.py`, `scripts/run-long-cuda-campaign.py`, `--device cuda`, checkpoint/resume и отчёты sessions.

**Нет:** испытания на конкретной RTX 3050, подтверждённой скорости/VRAM и настоящих длительных checkpoint. Скрипт кампании — инструмент, не свидетельство проведённого обучения.

**План:** CUDA preflight и малая операция; 1–2 тренировочных шага с моделью и реальными данными; восстановление checkpoint; VRAM budget / OOM recovery; замер throughput; проверка точности loss; затем долгие сессии с верифицируемыми логами, энергопотреблением и безопасной остановкой.

**Критерий:** реальные логи многочасовых/многодневных CUDA-сеансов, GPU/device id, исходный seed, SHA train, шаги, elapsed, VRAM, best checkpoint, независимая проверка восстановленного состояния. Не запускать облачный платный GPU без явного согласования стоимости.

### H. Качество русскоязычного диалога — P0, третий блокер

**Есть:** NLL/perplexity и изолированный тест, защищённый от повторной перезаписи отчёта. Это индикатор вероятности токенов, не доказательство собеседника.

**Дальше:** создать независимый русский benchmark с темами: дружелюбный диалог, правдивость, память, уточнения, многошаговые инструкции, бессмыслица и hallucination refusal, устойчивость к шуму, речь персонажа, безопасность, скорость; минимум 100 независимых промптов для слепого human baseline vs candidate; фиксировать победы/ничьи/регрессии, источники и конфликт интересов; тест на утечки из корпуса.

**Критерий:** измеримое, статистически обоснованное улучшение без критических регрессий; `EVAL`/`DIALOG`.

### I. Продуктовый чат, streaming и интеграция модели — P1

**Есть:** веб-чат и экспериментальный путь собственного checkpoint, частичные сценарии и проверочная инфраструктура.

**Дальше:** жизненный цикл model loader; безопасная очередь запросов; SSE streaming с отменой/таймаутом; сборка потока в историю; синхронизация аватара и частичного аудио; обработка обрыва сети и перезапуска; явное «модель не установлена», если accepted checkpoint отсутствует.

**Критерий:** 60+ сквозных сценариев с настоящим принятым checkpoint, корректной историей и отменой; `CHAT-001`/`004`.

### J. Голос и мультимодальное взаимодействие — P2/P3

**Цель:** опциональные распознавание голоса и синтез с согласиями, визуальными индикаторами и stop; синхронизация эмоций/анимации с реально произносимым текстом; не скрывать запись, cloud egress или стоимость.

**Статус:** UI/идеи, но полная end-to-end речевая приёмка отсутствует. Камера/экран — только при отдельном явном разрешении и наличии технического контракта.

**Критерий:** локальная/offline и опциональная cloud конфигурации, тесты разрешений и stop, доступность при отключённом микрофоне.

### K. Инициатива, события, цели и личность — P2

**Цель:** очередь событий и задач, реальное основание уведомления, тихие часы, лимиты и журнал причин; художественный образ кицунэ без претензий на реальные чувства; напоминания/возврат к проектам только по согласованию.

**Статус:** vision и частичные сценарии не равны автономному event-driven движку. Планировщик и долговечная очередь должны быть реализованы и протестированы отдельно.

**Критерий:** согласие/отзыв согласия, запрет выдуманных событий и молчание по умолчанию, audit trail, защита от повторных назойливых сообщений; `LIFE-001`–`003`.

### L. Инструменты, файлы и агентность — P2/P3

**Цель:** минимальные привилегии, sandbox, dry-run и подтверждение опасных действий, whitelist инструментов, журнал вызовов и откат, отсутствие самовольных расходов/изменений системы.

**Статус:** концепция/отдельные прототипы; полноценная безопасная агентная цепочка не принята.

**Критерий:** отдельные security tests, остановка и отзыв полномочий; `AGENT-001`, `SEC-001/002`.

### M. Облако, Cloud.ru и внешние сервисы — P2

**Цель:** опциональный Cloud.ru IAM, DPAPI-хранилище, ротация и удаление ключей, честное отображение расходов/проектов и разрешение каждого платного прогона; потоковый SSE с настоящим сервисом.

**Статус:** архитектура и отдельные инженерные шаги; настоящая сквозная приёмка IAM/SSE/расходов не подтверждена. Облако не должно подменять собственный локальный мозг.

**Критерий:** подтверждённая реальная авторизация, маскированные логи, защита секретов и ограничение счета; `CLOUD-001`–`006`.

### N. Лаборатория, саморазвитие и поколения модели — P3

**Цель:** экспериментальная изолированная ветка, reproducibility, фиксированный baseline и test, ресурсы/время, успешные и неуспешные гипотезы, явное решение человека о promotion/rollback.

**Статус:** есть benchmark/checkpoint-инфраструктура; автоматическое улучшение архитектуры и самообучение на своих ответах не доказаны и не должны включаться бесконтрольно.

**Критерий:** оценка улучшений до активации, запрет утечки теста, rollback предыдущего поколения; `LAB`, `PLASTIC`, `CURRICULUM`.

### O. Большая исследовательская программа — P4 / дальняя перспектива

В `planning/tasks.json` есть `WORLD`, `REASON`, `MULTIAGENT`, `SIM`, `SCIENCE`, `AGI`, `META`, `HYPER`, `GOV`, `SCALE`, `ALIGN`. Это **спекулятивные долгосрочные исследовательские цели**, не реализованные возможности. Не начинать масштабирование, «сознание» или широкую автономию, пока базовая русская модель, безопасность, память и продуктовые тесты не приняты. Никаких ложных заявлений об интеллекте или чувствах.

| **R2: оценка** | доказанное улучшение русской речи | R1 | held-out test, blind reviewers, регрессии |

| **R4: данные и надёжность** | долговечная история, полноценный restore, updater QA | storage/API | stress, миграции, аварийное восстановление |
| **R5: голос и персонаж** | opt-in voice, синхронный аватар и доступный UI | R3 | тесты микрофона, стопа и задержки |
| **R6: инициатива и инструменты** | permissioned event engine и ограниченный агент | R4/R5 + security | аудит действий, quiet hours, откат |
| **R7: лаборатория поколений** | безопасная проверяемая эволюция модели | R2/R3/R6 | воспроизводимый benchmark и ручное promotion |
| **R8: расширенная исследовательская программа** | только научно обоснованные новые способности | R7 | независимая оценка и контроль рисков |

*Даты завершения волн не назначены: они зависят от фактических данных, оборудования, испытаний и ресурсов. Волны R3–R4 можно частично готовить параллельно, но не объявлять продукт готовым раньше R2 и Windows QA.*

## 4. Реестр задач и расхождения, которые нельзя скрывать

На момент этого среза `planning/tasks.json` содержит **100 задач**. Реестр старше поздних нейронных PR: `snapshot.date=2026-10-18`, а `BRAIN-001`–`007` остаются `todo` несмотря на реализацию существенных подкомпонентов. Для исправления расхождения нужен отдельный аудит каждой задачи с `evidence` и конечными acceptance tests.

**Правило статуса:** код + тесты + принятый результат, с различением CPU CI, реального Windows и настоящего CUDA. Только после этого обновлять `planning/tasks.json`; контрольная точка выше — не акт приёмки всего проекта.

## 5. Команды, которыми возобновляем работу

```powershell
# 1. Реальная CUDA-диагностика на целевом Windows/GPU (с отдельным PyTorch окружением)
python scripts/probe-language-cuda.py --output cuda-probe.json --require-cuda

# 2. После аудита разрешённых русских данных: тренировочная кампания
python scripts/run-long-cuda-campaign.py --records corpus.json --output training-campaign --device cuda --total-steps 100000 --session-seconds 3600 --max-sessions 48

# 3. Отдельная финальная test-оценка после штатного эксперимента run-language-experiment.py
python scripts/finalize-language-test.py --records corpus.json --experiment-dir training-run
```

**Замечание:** команда финальной оценки выше ожидает структуру `training-run/experiment.json`, создаваемую `run-language-experiment.py`. Многосессионная кампания использует другой manifest/формат отчётов; связывание её с финальным тестом — отдельная интеграционная задача перед фактической приёмкой.

## 6. Решение для следующего исполнителя

1. Открыть последнюю ветку `main`, сверить `planning/tasks.json` и этот срез с живым кодом.
2. **Не создавать следующую декоративную систему метрик** вместо реального обучения. Получить законные данные или реальный доступ к RTX 3050; документировать блокер, если их нет.
3. Провести CPU smoke и физический GPU pilot с точным checkpoint и контрольным продолжением.
4. При успешном pilot запустить длительный прогон, сохранить фактические отчёты, затем провести blind benchmark.
5. Параллельно закрывать критические Windows/SQLite риски без изменения активной модели.
6. После доказанной приёмки — интеграция с чатом, затем голос, инициатива и агентность.

**На чём остановились одной фразой:** инфраструктура Yorika создана значительно дальше начального прототипа, но переход от инженерной основы к реальному русскоязычному интеллекту остановлен на отсутствии большого подтверждённого корпуса, проведённого GPU-обучения и независимого доказательства качества.
